# Security

## Admin access
- Supabase Auth is **only for administrators**. Public sign-up is disabled in the project settings (`[auth] enable_signup = false` for production, to be verified in P7-01).
- Access requires a valid session **and** a row in `admin_user` (roles editor < reviewer < admin). Being authenticated alone grants nothing beyond anon access.
- The site is a static export (ADR-0006), so there's no server to check admin access. `/admin` pages are client-rendered, and **their JavaScript is public**. Access control rests entirely on RLS policies and on `SECURITY INVOKER` RPCs that check `is_admin()`. Never rely on hiding admin code or routes.
- Proposal: MFA required for admin accounts. Session lifetime to be decided in P7-01.
- **As built (P7, ADR-0012):** sign-in is email and password with the public anon key. Local `config.toml` has `enable_signup = true` **because the local email provider must be enabled for password sign-in**; the end-to-end spec proves a stranger cannot sign up (the response is an error) and that a signed-in user who is not on `admin_user` sees nothing. **For the hosted projects the owner must confirm sign-ups are disabled in the dashboard** (Authentication, Sign In / Providers, "Allow new users to sign up" off), and create each administrator in the dashboard. Not built: MFA, an admin-user management page, password reset by email (needs an email provider).

## Database policies
- RLS is enabled on every `public` table. Tables without RLS fail CI (a pgTAP check over `pg_tables`).
- anon can only SELECT published or active rows, and has no direct INSERT. Public writes (feedback, click counts) go only through Edge Functions, which validate and then write with credentials held as Supabase function secrets. Admin writes are ordinary table writes and RPCs under the admin's session, checked by RLS.
- `SECURITY DEFINER` functions must `SET search_path` and be reviewed. Everything else is `SECURITY INVOKER`.
- The pipeline uses a dedicated Postgres role with only the grants it needs, never the service role inside browser code.
- **Pipeline (P8, ADR-0013).** The `pipeline` role is `NOLOGIN`; the owner creates a login that is a member of it (a statement is in the migration's comments) and stores its connection string as the GitHub secret `PIPELINE_DATABASE_URL`. It reads the reference tables, companies, offices, sources and feeds, inserts and updates jobs, inserts link checks, and calls `record_link_check`, `record_heartbeat`, and `missed_heartbeats`. It cannot read `audit_log`, `admin_user`, `submission`, `feedback_rate`, or `link_click_daily`, and cannot call `publish_now`, `import_commit`, `record_click`, `submit_feedback`, or the sweep and upkeep functions (pg_cron runs those). `verification_check` is partitioned by month; RLS is on and grants are revoked on every partition, and a pgTAP test (`09_pipeline`) proves a role without the grant is refused when it reads the parent table (the anonymous API probe in `test:admin` covers anon). The runner fetches only URLs from the database, with the SSRF rules in `scripts/pipeline/fetch.py` (https, no credentials in the URL, public addresses only, redirects re-checked, bounded bodies, timeouts). **Residual risk:** a hostile DNS server could answer differently between the address check and the connection (rebinding); the runner holds only the pipeline login, so the impact is a request to an internal address whose reply nothing stores.
- **Anonymous probe (P9-02).** `npm run test:admin` calls the open REST API with the anon key and fails if it can read a draft company, `admin_user`, `audit_log`, `submission`, `feedback_rate`, `link_click_daily`, `heartbeat`, `verification_check`, `job_feed`, `source`, `site_state`, or `import_batch`, can write to `company`, `job`, `city`, or `submission`, or can call `publish_now`, `record_click`, `submit_feedback`, `import_commit`, `sweep_stale_jobs`, or `missed_heartbeats`.

## Secrets
- Never commit credentials. `.env*` is git-ignored except for `code/.env.example`.
- Browser-safe values: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (or its publishable-key equivalent), `NEXT_PUBLIC_GEOAPIFY_KEY` (to be restricted by referrer in Geoapify MyProjects; **unrestricted on 1 Oct 2026**, see ADR-0008), and `NEXT_PUBLIC_TURNSTILE_SITE_KEY`.
- Server-only values: `SUPABASE_SERVICE_ROLE_KEY`, `TURNSTILE_SECRET_KEY`, the GitHub token for `request-rebuild`, `PIPELINE_DATABASE_URL`, and the Cloudflare API token for deploys. They live **only** in Supabase function secrets and GitHub encrypted secrets. The Next.js build sees only `NEXT_PUBLIC_*` values, and it reads the snapshot with the anon key, so RLS limits it to published data.
- CI greps the static output (`out/`) for secret-looking strings before deploying (see testing.md).
- CI runs a secret scan (for example gitleaks; the tool choice is open).

## Public forms (reports, suggestions)
- The `submit-feedback` Edge Function verifies the Turnstile token (`siteverify`) **before** any insert. The expected hostname and action are checked, and a token is never reused.
- Zod validation, length limits, a required source URL for suggestions, and no PII fields.
- Rate limit inside the Edge Function (proposal: 5 submissions per client per hour). The client key is a salted, daily-rotated hash; no raw IP is stored. The Cloudflare WAF doesn't sit in front of Supabase, so this replaces the plan's WAF rule.
- The response contains only a receipt ID. Nothing is published without review.
- **As built (P8-04, ADR-0013):** the order in `submit-feedback` is origin check, strict Zod schema (an unknown field is a 400), Turnstile `siteverify` with the action (`feedback`) and hostname checked, then the rate-limited insert through `submit_feedback` (service role only; the limit is 5 stored submissions an hour for one key, a refused call stores nothing). The form never shows a status code: it has words for 400, 403, 429, and the rest. Reviewers read each submission as plain text (no HTML) in the admin Review page; a link a visitor sends is shown with `rel="noopener noreferrer"`. A suggestion is a lead only: it is never added to the map without an administrator creating the company. Secrets: `TURNSTILE_SECRET_KEY`, `FEEDBACK_SALT`, `ALLOWED_ORIGINS` as Supabase function secrets; `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is public. **Not verified:** the real Cloudflare `siteverify` (the local test uses a stand-in), and Turnstile in the real widget.

## Outbound links and content
- Apply and website URLs must be `https` and match the company domain or a known ATS host. This is checked **at build time**; a failing URL fails the build. Links point to the stored URL unchanged (no redirect service). The `click` beacon sends only the job or company ID and the link kind. **As built (P6-03):** `lib/links.ts` checks every URL when the build reads the datasets: https only, no user name or password, no `localhost` or IP address, and the host must be the company's domain (or a subdomain) or, for careers pages and Apply links, a host on `KNOWN_ATS_HOSTS` (a look-alike such as `evil-acme.example` or `greenhouse.io.evil.test` does not match). A failing URL fails the build with the company and the link named. The `click` Edge Function is described in [ADR-0011](decisions/0011-click-beacon.md): JWT verification is off (a beacon cannot send the header), so it checks the method, an allow-listed `Origin`, a 512-byte limit, and a strict Zod schema, and a refused target answers 204 so ids cannot be probed. Counts can be inflated by a script that sets the header; they are for trends.
- Strict CSP, sanitised descriptions, and `rel="noopener noreferrer"`. **As built (P9-02, ADR-0014):** the policy is a `<meta http-equiv="Content-Security-Policy">` written into every page after the build, with the SHA-256 of each inline script (no `'unsafe-inline'` or `'unsafe-eval'` for scripts), because a rule per page would exceed the 100 header rules. It allows `'self'`, `https://maps.geoapify.com`, Turnstile, and the Supabase origin; `worker-src 'self' blob:` (MapLibre). Framing is refused by `X-Frame-Options: DENY` in `public/_headers`. `tests/e2e/csp.spec.ts` fails on any violation on the key pages and proves an injected inline script and a foreign script are blocked.
- Company logos are fetched by the map from our own Storage host only. `allowedHosts` is set to that host once the dataset exists (P4-01), so a bad logo URL in the data cannot make a visitor's browser call a third party and reveal their IP address. Logos must be `https:` (or a same-origin path), raster (PNG, JPEG, WebP, GIF, AVIF), and at most 1 MB; they are fetched with no cookies and no referrer. SVG is refused. The CSP `connect-src` must list the Storage host, and Storage must send CORS headers (the layer reads the pixels). [Proposal until P4-01]

## Privacy
- There is no visitor account and no visitor PII. Click logs contain no IP address or user identifier (the retention and analytics tool are decided in D-07).
- Founder names are limited to what the company itself publishes (D-03).
