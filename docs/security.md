# Security

## Admin access
- Supabase Auth is **only for administrators**. Local `config.toml` has `[auth] enable_signup = false`; `[auth.email] enable_signup = true` only keeps the email provider on for password sign-in. **For each hosted project the owner must turn sign-ups off in the dashboard.**
- Access requires a valid session **and** a row in `admin_user` (roles editor < reviewer < admin). Being authenticated alone grants nothing beyond anon access.
- The site is a static export (ADR-0006), so there's no server to check admin access. `/admin` pages are client-rendered, and **their JavaScript is public**. Access control rests entirely on RLS policies and on `SECURITY INVOKER` RPCs that check `is_admin()`. Never rely on hiding admin code or routes.
- **MFA is required for administrators (P9-13, ADR-0020; built 7 Oct 2026).** `is_admin()` (final version in `20261007140000_admin_session_checks.sql`) is true only when the token says `aal2`, its session row is live in `auth.sessions` (signing out ends it; `not_after` is honoured), and the user still has a verified factor (removing it ends access at once); `aal2` is which Supabase Auth issues after the user has entered a TOTP code from an authenticator app in that session. Every admin policy, admin RPC, and gate goes through `is_admin()`, so a password-only (`aal1`) session can read its own `admin_user` row (to be shown the code screen) and nothing else an administrator could. The admin page asks for the code after the password, or, for an administrator with no factor yet, shows a set-up screen (QR code and key). Local `config.toml` enables TOTP enrolment and verification. **For the hosted projects the owner must enable TOTP MFA in the dashboard** (Authentication, Multi-Factor). Supabase lists TOTP MFA as available on every plan; check that this is still true before relying on it, and phone (SMS) MFA is not used. **A lost authenticator** is recovered by another administrator removing that user's factor in the dashboard (Authentication, Users), after checking who is asking; the user then sets up a new one. Session lifetime is still Supabase's default.
- **As built (P7, ADR-0012):** sign-in is email and password with the public anon key. Local `config.toml` keeps the email provider on (`[auth.email] enable_signup = true`) for password sign-in while `[auth] enable_signup = false`; the end-to-end spec proves a stranger cannot sign up (the response is an error) and that a signed-in user who is not on `admin_user` sees nothing. **For the hosted projects the owner must confirm sign-ups are disabled in the dashboard** (Authentication, Sign In / Providers, "Allow new users to sign up" off), and create each administrator in the dashboard. Not built: an admin-user management page, password reset by email (needs an email provider).

## Database policies
- RLS is enabled on every `public` table. Tables without RLS fail CI (a pgTAP check over `pg_tables`).
- anon can only SELECT published or active rows, and has no direct INSERT. Public writes (feedback, click counts) go only through Edge Functions, which validate and then write with credentials held as Supabase function secrets. Admin writes are ordinary table writes and RPCs under the admin's session, checked by RLS.
- `SECURITY DEFINER` functions must `SET search_path` and be reviewed. Everything else is `SECURITY INVOKER`.
- The pipeline uses a dedicated Postgres role with only the grants it needs, never the service role inside browser code.
- **Pipeline (P8, ADR-0013).** The `pipeline` role is `NOLOGIN`; the owner creates a login that is a member of it (a statement is in the migration's comments) and stores its connection string as the GitHub secret `PIPELINE_DATABASE_URL`. It reads the reference tables, companies, offices, sources and feeds, inserts and updates jobs, inserts link checks, and calls `record_link_check`, `record_heartbeat`, `missed_heartbeats`, `record_feed_job_evidence`, `evidence_due`, and `record_evidence_check`; it inserts `feed_event` rows. **Since `20261007150000` the database itself refuses a job the pipeline lists (or whose public facts it changes) unless the job comes from an approved, active feed of a published company and has claimed or reviewed evidence for title, employer, location, and link** (`pipeline_job_gate`, checked at commit); moving a listed job between active and suspect, or closing it, needs nothing more. It cannot read `audit_log`, `admin_user`, `submission`, `feedback_rate`, or `link_click_daily`, and cannot call `publish_now`, `import_commit`, `record_click`, `submit_feedback`, or the sweep and upkeep functions (pg_cron runs those). `verification_check` is partitioned by month; RLS is on and grants are revoked on every partition, and a pgTAP test (`09_pipeline`) proves a role without the grant is refused when it reads the parent table (the anonymous API probe in `test:admin` covers anon). The runner fetches only URLs from the database, with the SSRF rules in `scripts/pipeline/fetch.py` (https, no credentials in the URL, public addresses only, redirects re-checked, bounded bodies, timeouts). **Residual risk:** a hostile DNS server could answer differently between the address check and the connection (rebinding); the runner holds only the pipeline login, so the impact is a request to an internal address whose reply nothing stores.
- **Anonymous probe (P9-02).** `npm run test:admin` calls the open REST API with the anon key and fails if it can read a draft company, `admin_user`, `audit_log`, `submission`, `feedback_rate`, `link_click_daily`, `heartbeat`, `verification_check`, `job_feed`, `source`, `site_state`, or `import_batch`, can write to `company`, `job`, `city`, or `submission`, or can call `publish_now`, `record_click`, `submit_feedback`, `import_commit`, `sweep_stale_jobs`, or `missed_heartbeats`.

## Secrets
- Never commit credentials. `.env*` is git-ignored except for `code/.env.example`.
- Browser-safe values: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (or its publishable-key equivalent), `NEXT_PUBLIC_GEOAPIFY_KEY` (to be restricted by referrer in Geoapify MyProjects; **unrestricted on 1 Oct 2026**, see ADR-0008), and `NEXT_PUBLIC_TURNSTILE_SITE_KEY`.
- Server-only values: `SUPABASE_SERVICE_ROLE_KEY`, `TURNSTILE_SECRET_KEY`, the GitHub token for `request-rebuild`, `PIPELINE_DATABASE_URL`, and the Cloudflare API token for deploys. They live **only** in Supabase function secrets and GitHub encrypted secrets. The Next.js build sees only `NEXT_PUBLIC_*` values, and it reads the snapshot with the anon key, so RLS limits it to published data.
- CI greps the static output (`out/`) for secret-looking strings before deploying (see testing.md).
- CI runs a secret scan with gitleaks 8.30.1 (checksum-pinned, full history, `.github/workflows/ci.yml`).

## Public forms (reports, suggestions)
- The `submit-feedback` Edge Function verifies the Turnstile token (`siteverify`) **before** any insert. The expected hostname and action are checked, and a token is never reused.
- Zod validation, length limits, a required source URL for suggestions, and no PII fields.
- Rate limit inside the Edge Function (proposal: 5 submissions per client per hour). The client key is a salted, daily-rotated hash; no raw IP is stored. The Cloudflare WAF doesn't sit in front of Supabase, so this replaces the plan's WAF rule.
- The response contains only a receipt ID. Nothing is published without review.
- **As built (P8-04, ADR-0013):** the order in `submit-feedback` is origin check, strict Zod schema (an unknown field is a 400), Turnstile `siteverify` with the action (`feedback`) and hostname checked, then the rate-limited insert through `submit_feedback` (service role only; the limit is 5 stored submissions an hour for one key, a refused call stores nothing). The form never shows a status code: it has words for 400, 403, 429, and the rest. Reviewers read each submission as plain text (no HTML) in the admin Review page; a link a visitor sends is shown with `rel="noopener noreferrer"`. A suggestion is a lead only: it is never added to the map without an administrator creating the company. Secrets: `TURNSTILE_SECRET_KEY`, `FEEDBACK_SALT`, `ALLOWED_ORIGINS` as Supabase function secrets; `NEXT_PUBLIC_TURNSTILE_SITE_KEY` is public. **Not verified:** the real Cloudflare `siteverify` (the local test uses a stand-in), and Turnstile in the real widget.
- **Refused rather than worked around (8 Oct 2026):**
  - **A missing or short salt.** `FEEDBACK_SALT` shorter than 32 characters (or unset) makes the function answer 503 to every submission, before Turnstile or the database is touched, and log the reason at start-up. An empty salt used to make every rate-limit key guessable.
  - **No trustworthy client address.** The rate-limit key comes only from an entry the platform's own proxy wrote: the `TRUSTED_PROXY_HOPS`-th entry from the right of `CLIENT_IP_HEADER` (a header the edge sets whole, such as `cf-connecting-ip`, uses 1). Entries to its left are written by the client and ignored, so a visitor can no longer choose their own key. The address must be well-formed. A request with none is refused with 503, instead of every such request sharing one key.
  - **No default: the form stays off until the hosted check is done.** With `CLIENT_IP_HEADER` and `TRUSTED_PROXY_HOPS` unset, `submit-feedback` refuses every submission with 503 and says why at start-up. Setting only one of them is a start-up error. The values are not guessed. A community report (Supabase discussion #34647, April 2025, no official answer) says a client-sent `X-Forwarded-For` keeps its value with the real address appended, and that `cf-connecting-ip` held the real address. That is a lead for the check, not a setting.
  - **The hosted check, before feedback is enabled on a project:**
    1. Deploy a temporary function, on that project only, that returns the request's `x-forwarded-for`, `cf-connecting-ip`, `x-real-ip` and `forwarded` headers.
    2. Call it from a machine whose public address you know: plainly; with `X-Forwarded-For: 203.0.113.1`; with `X-Forwarded-For: 203.0.113.1, 198.51.100.2`; and with `CF-Connecting-IP` and `X-Real-IP` set to fake values.
    3. Choose the header and position that always show the real address and never a sent value. Record the results in progress.md. Set `CLIENT_IP_HEADER` and `TRUSTED_PROXY_HOPS`, then delete the temporary function.
    4. Repeat a spoofed request against `submit-feedback` and confirm that six submissions in an hour are refused however `X-Forwarded-For` varies.
  - Locally, the admin e2e sets `x-forwarded-for` and 1, because the local gateway (Kong) appends the address it saw. That says nothing about hosted Supabase.
- **Pilot preview copies hold SIMULATED reviews (8 Oct 2026).**
  - **What the copy holds:** `scripts/pilot/preview-db.mts` marks the throwaway copy's pilot evidence reviewed, so that the listing rule shows the records. The reviewer is a stand-in, `pilot-preview-stand-in@local.test`, whose metadata says `simulated`. Each row is listed in `pilot_preview.simulated_review`. Every original evidence field is kept, and the copy is marked with `pilot_preview.marker`.
  - **Every layer refuses it** except the local preview build it was made for:
    - the dataset build refuses a marked database without `PILOT_PREVIEW=1`, and always in a release (`previewCopyRefusal`);
    - `PILOT_PREVIEW=1` needs a database on this machine (`pilotPreviewRefusal`), and `check-deploy-env` refuses it for staging and production;
    - a preview's `manifest.json` carries `pilot_preview: true`, which the launch gate and the data refresh refuse;
    - the production smoke check fails if a page carries the preview banner.
  - **Checked on the test stack:**
    - a staging-style build and a release build of the copy were refused, and a real preview build's manifest failed the launch gate;
    - the source database's evidence stayed unreviewed.
  - Unit tests: `tests/unit/feedback-handler.test.ts` (spoofed entries give the same key; missing salt or address refused before Turnstile; hop counts; `CF-Connecting-IP`).

## Outbound links and content
- Apply and website URLs must be `https` and match the company domain or a known ATS host. This is checked **at build time**; a failing URL fails the build. Links point to the stored URL unchanged (no redirect service). The `click` beacon sends only the job or company ID and the link kind. **As built (P6-03):** `lib/links.ts` checks every URL when the build reads the datasets: https only, no user name or password, no `localhost` or IP address, and the host must be the company's domain (or a subdomain) or, for careers pages and Apply links, a host on `KNOWN_ATS_HOSTS` (a look-alike such as `evil-acme.example` or `greenhouse.io.evil.test` does not match). A failing URL fails the build with the company and the link named. The `click` Edge Function is described in [ADR-0011](decisions/0011-click-beacon.md): JWT verification is off (a beacon cannot send the header), so it checks the method, an allow-listed `Origin`, a 512-byte limit, and a strict Zod schema, and a refused target answers 204 so ids cannot be probed. Counts can be inflated by a script that sets the header; they are for trends.
- Strict CSP, sanitised descriptions, and `rel="noopener noreferrer"`. **As built (P9-02, ADR-0014):** the policy is a `<meta http-equiv="Content-Security-Policy">` written into every page after the build, with the SHA-256 of each inline script (no `'unsafe-inline'` or `'unsafe-eval'` for scripts), because a rule per page would exceed the 100 header rules. It allows `'self'`, `https://maps.geoapify.com`, Turnstile, and the Supabase origin; `worker-src 'self' blob:` (MapLibre). Framing is refused by `X-Frame-Options: DENY` in `public/_headers`. `tests/e2e/csp.spec.ts` fails on any violation on the key pages and proves an injected inline script and a foreign script are blocked.
- Company logos are fetched by the map from our own Storage host only. **As built, the explorer does not pass `allowedHosts` to the logo loader** (`map/explorer-map.ts`): logo URLs are always built from the Storage host by `lib/data/logo.ts`, and the CSP (`img-src`, `connect-src`: self and the Supabase origin) is the effective guard against a third-party request. Logos must be `https:` (or a same-origin path), raster (PNG, JPEG, WebP, GIF, AVIF), and at most 1 MB; they are fetched with no cookies and no referrer. SVG is refused. The CSP `connect-src` lists the Storage host, and Storage must send CORS headers (the layer reads the pixels; not verified on a hosted project).
- **Logo uploads (P9-21, [ADR-0024](decisions/0024-logo-storage-and-provenance.md), 7 Oct 2026):** two buckets, each raster-only (PNG, JPEG, WebP, GIF, AVIF) up to 1 MB. Editors (`aal2`) upload only to the **private** `company-logos-pending`, only to `<company id>/<sha-256>.<ext>`, with a provenance record (`logo_asset`: source, basis, terms quote, storage/display/atlas permissions). A reviewer approves or rejects it (`review_logo`). **Only after approval** may a reviewer copy it into the public `company-logos` bucket (SEC-2, `20261007150000`: an undecided or rejected upload can never be copied), and it becomes the logo only through the `activate-logo` Edge Function (`20261007160000`): a reviewer's request is recorded (`request_logo_activation`), the function downloads the pending upload and the public copy with the service key and computes the **SHA-256 of their bytes on the server**, and `complete_logo_activation` (service role only) accepts only if both equal the hash the upload's key names. No hash or metadata a browser sends is compared; a client-supplied hash is refused outright. `company.logo_key` can point only at an approved, activated upload. Only admins delete files.
- **Callers with no signed-in user (SEC-4, `20261007150000`).** The gates identify the real caller (`caller_role()`: the `role` setting PostgREST or `set role` sets, else the login). The database owner (migrations, the seed, pg_cron, the dashboard SQL editor) is trusted. `service_role` (held by the Edge Functions) may record claims and close jobs but **may not** insert evidence marked reviewed, review evidence, publish or unpublish, change a public fact without reviewed evidence, approve a feed, or set a logo key. Edits by an editor to a public company's tags or sectors, or a public job's cities, now need reviewed evidence on UPDATE as well as INSERT and DELETE (SEC-1). Regression tests: `supabase/tests/database/16_security_gaps.test.sql`.

## Privacy
- There is no visitor account and no visitor PII. Click logs contain no IP address or user identifier (the retention and analytics tool are decided in D-07).
- Founder names are limited to what the company itself publishes (D-03).
